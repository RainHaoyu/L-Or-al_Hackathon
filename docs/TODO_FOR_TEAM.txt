第一组：已定位的确切缺陷（建议最先修，都是小改动但影响真实功能）

【1-1】失嗅模式的 AI 文案没有走后端（前端写死 mode:'normal'）

位置：web/src/components/AnalyzeFlow.tsx 第 126 行附近

现状：调用后端 /analyze 时把 mode 参数写死成 'normal'，没有使用顶栏选中的模式。
后果：用户在顶栏切到「失嗅模式」时，后端仍按 normal 生成通感文案；
      失嗅模式那段更长的文案其实是前端 Vision.tsx 用本地 buildSynesthesia 拼出来的。
      也就是说「失嗅模式走 AI」这个能力实际上没生效。

修法：从 useApp() 取出 mode，传给 api.analyze 的 mode 字段。
      AnalyzeRequest 契约里已经有 mode 字段（api/app/schemas.py 第 96 行），
      后端 analyze 也已经把它传给 llm.synthesize，所以后端不用改。

坑（重要）：修完这一条会连带触发下一条 1-2，必须一起改，否则失嗅模式会一直超时。

验收：切到失嗅模式后，报告页的通感文案 model 字段显示 qwen-max（而非 template），
      且文案是四五句的长文（不是模板那种一两句拼接）。


【1-2】前端超时需要按模式区分（与 1-1 是同一批工作）

位置：web/src/lib/api.ts，以及 web/src/components/AnalyzeFlow.tsx 的调用处

现状：api.ts 里 TIMEOUT 是全局 15 秒；后端 llm.py 每档超时 5 秒（共两档串行，最坏 10 秒）。

实测数据（2026-10-05，qwen-max 真实调用，18 个样本）：
    normal   模式：2944 - 4499 毫秒，输出 85 - 126 字
    sensitive模式：2811 - 3574 毫秒，输出 84 - 126 字
    anosmia  模式：7691 - 9588 毫秒，输出 296 - 371 字

也就是说失嗅模式因为 prompt 要求「四五句、每句都要具体意象」，输出长三倍、耗时也长三倍。
如果把 mode 改成真实模式（1-1）而超时仍是 5 秒，失嗅模式会 100% 落回规则模板。

修法：把超时做成按模式取值。
    建议 normal 与 sensitive 用 6 秒（实测上限约 4.5 秒，留余量），
    anosmia 用 12 秒（实测上限约 9.6 秒，留余量）。
    后端 llm.py 的 _TIMEOUT 也要同步按模式区分，两个数字必须满足：
    前端超时 > 后端单档超时 × 档数（当前是 2 档）。

验收：三种模式都能拿到 qwen-max 的真实文案；把后端关掉时，三种模式都能在超时后
      正常回退本地引擎（不卡死、不报错）。


【1-3】后端测试没有隔离网络，设了 API Key 就会真的调用百炼

位置：api/tests/test_api.py（以及任何会走到 llm.synthesize 或识别层的用例）

现状：测试直接读进程环境变量 DASHSCOPE_API_KEY。如果开发机上设了这个变量，
      测试会真的发请求给百炼。
实测：设了 Key 时会真的发出请求并消耗额度，测试结果因此依赖网络与账户状态。
      （更正：早期把"511 秒"归因于 Key 是错的——无 Key 全量实测也要 512 秒，
       单次 analyze 的引擎开销就有 4.4-5.0 秒，慢的是引擎本身，见 3-3。）

修法：在测试里隔离掉。两种做法任选：
      a) 用 pytest 的 monkeypatch 在每个相关用例前删除 DASHSCOPE_API_KEY
         （monkeypatch.delenv("DASHSCOPE_API_KEY", raising=False)），
         或者在 conftest.py 里做全局 autouse fixture；
      b) 把 httpx 调用 mock 掉，让测试完全不碰网络。
      推荐 a，改动小且能覆盖所有用例。

验收：在设了 DASHSCOPE_API_KEY 的环境下跑 pytest，耗时与不设时一致（约 130 秒），
      且不会产生任何外部请求。


【1-4】IFRA 禁用清单解析仍有 CAS 错位隐患（已修一半，还剩根因）

位置：web/scripts/build_data.py 的 build_ifra 函数（禁用清单那段，约 291-310 行）

背景：源 xlsx 的禁用清单区（H/I/J 三列）在导出时整体错位一行，
      H 列的分段其实属于「上一行」的化合物，导致按行拼出来的 CAS 张冠李戴。
      7 条里 5 条错误，其中 1 条校验位非法（薄荷内酯 223743-5-7）。

已做：加了一张 BANNED_CAS_CORRECTIONS 人工核对表 + cas_checksum_ok 校验位函数，
      修正了那 5 条，并保留 casSource 字段记录源值以便审计。

还剩：解析逻辑本身仍是「按行拼 H/I/J」，只是靠人工表兜住了已知错误。
      如果上游 xlsx 换版本，错位会以新形式出现，人工表兜不住。

修法：把「按行列位置解析」改成「按数据模式解析」——例如先扫描整张表，
      识别出 CAS 的实际列布局，再按化合物名对齐；或者
      解析后强制过一遍校验位，非法即报错中止（而不是静默落盘错误值）。

验收：把 数据层/IFRA 那份 xlsx 人为改动一行（比如插入空行）后重跑管线，
      要么产出仍然正确，要么明确报错，不允许静默产出错误 CAS。


【1-5】成分匹配在别处仍是子串匹配（已修毒理与 IFRA，还剩词典类）

位置：web/src/lib/aura.ts 与 api/app/data.py

背景：项目里所有「成分名 → 条目」的查找原本都是「归一化后子串包含 + 首个命中」。
      这类匹配在长名包含短名时会误判。已经实测出并修掉的问题包括：
        毒理表    Isoeugenol 被判成丁香酚（真实值小 23 倍，危险方向）
        毒理表    Hexyl/Amyl Cinnamal 被判成肉桂醛
        IFRA 限值 异丁香酚 0.05% 被判成丁香酚 0.5%（偏宽松 10 倍，可能漏判超标）
        IFRA 限值 α-己基肉桂醛 4% 被判成肉桂醛 0.05%（偏严格 80 倍，误报红灯）
        IFRA 禁用 Lilial / HICC / Lyral 完全匹配不上（漏检禁用物）
      修法是「匹配键按长度降序，取首个命中」，别名落在数据里由前后端共读。

还剩：EU26 标注清单、IgE 速发材料、香材词典、CAS 词典这几处的查找，
      虽然也改成了最长优先，但**没有逐条验证过**是否还有误匹配。
      另外 lookup_ifra_limit / lookup_banned 的匹配目前只在 Python 侧重建了索引，
      前端 aura.ts 的对应实现要确认是否同步一致。

修法：对每类词条做一次「交叉探测」——用每条自己的名字去查，看是否命中自己。
      没命中自己或命中了别人的，逐条定位并修正，然后补回归测试。
      这个探测脚本很便宜，写一次能把四类表全扫一遍。

验收：四类词条各自「用自己名字查自己」的命中率 100%，且有回归测试锁住。
